## 页面需要的数据

页面读取 `data/voyage.json`，结构如下，第 0 天是 2021-02-03。`src/data.ts` 在构建时导入这个文件，转成同一文件里的 `VoyageData`：

```js
{
  total:     [每天的整数],   // 当天结束时的大航海总数
  followers: [每天的整数],   // 粉丝数
  live:      [每天 0 或 1],  // 当天是否开播；直播档案缺的区间按她的直播预告推断，见下文「开播日」
  named:     [{ start, level, medal, id, acc, name }],  // 今天在册的名单
             // start = 这条船开始有名字的那天（可带小数），算法见下文「采集」的合成规则
             // level 1 总督、2 提督、3 舰长；medal 粉丝牌等级；id 是 UID 的哈希，见下文「UID 的 id」
             // acc = 快照当天的陪伴天数：B 站正值或历史回填的推定值；null 是未知
             // name = 昵称，清理过；'' 是没有名字（快照里还没有昵称，或这个人要求删掉）
             // 任何一天有名字的船都不超过当天的 total，其余是无名之舰
  anchors:   { total: [[天, 数值]], followers: [[天, 数值]] },  // 核实过的数字，画成白点
  meta:      { day0, named_at, named_by, accompany, live_by_posts, from: { total, followers, live } }
             // 第 0 天、名单的抓取时间、三种 start 各有多少人、按直播预告推断开播的区间 [[首日, 末日]]、
             // 各序列真正有数据的第一天（live 是直播档案的第一场）
}
```

采集程序生成的 `data/voyage.json` 就是这个结构。Vite 构建时把它打包进 `dist/index.html`，所以重新合成数据后，要再运行一次 `npm run build`。数组有多少天，页面就播放到哪一天。页面暂时不用 `meta`；`id` 只在观众按 UID 找船时比对。

每座月份鸟居的档位（素木、朱漆、插火羽）由 `total` 的当月平均在所有月份里的排名算出，季节只看月份，都不需要另外的数据。

### 页面上的数字

左上角的读数说的是播放到的那一天，第 d 天的数字都从上面的字段算出：

| 读数 | 意思 | 算法 |
|---|---|---|
| 大航海 · 当天在船 | 那天船上的总人数，三档合计 | `total[d]` |
| 陪伴至今 | 那天在船、一直留到今天的人 | `start` 早于 d + 1 的人数；按 `level` 分成舰长和提督·总督 |
| 后来离开 | 那天在船、后来离开了的人，画成无名之舰 | 大航海减陪伴至今 |
| 其中陪伴一年以上、半年以上、满月以上 | 陪伴至今里，到那天陪伴满 365、180、30 天的人 | 那天的陪伴天数 = `acc` −（最后一天 − d） |
| 篝火 | 她最近开播的频率，写成旺、燃、微、熄 | `live` 按「几天前」以 10 天为时间常数指数加权的平均（`src/data.ts` 的 `LAMP`），0.85 以上旺，0.5 以上燃，0.2 以上微 |

所以过去某天的「舰长」不是那天全部的舰长，而是当前成员中按下文算法推定当时在船的那部分。陪伴天数优先用 B 站的正值，异常零值按下文规则回填；没有依据时显示「陪伴天数未知」，不计入光柱和周年刻字。陪伴天数可能包含以前的任期，上舰日和是否连续在册是结合总数曲线的推断，不是逐人历史记录。2026-10-22 的名单里，陪伴满 30 天的有 134 人，其中算法把 14 人安排为连续在舰，其余 120 人安排为离开后返回。

## 来源

| 数据 | 来源 | 说明 |
|---|---|---|
| 今天的名单与陪伴天数 | B 站 `xlive/app-room/v2/guardTab/topListNew?roomid=22748536&ruid=2094031249&page=N&page_size=30` | 返回总数、陪伴天数 `accompany`、等级 `uinfo.guard.level`、粉丝牌等级 `uinfo.medal.level`；只有当前在册的人，到期时间为空 |
| 每日大航海总数、粉丝数 | vtbs.moe 的 bulkGuard、bulkActive | 从 2021-02-03 开始 |
| 新上舰事件 | 直播间 websocket 的 `GUARD_BUY`、`USER_TOAST_MSG` | 只能从开始监听起记录 |
| 开播日 | HANE 的直播档案；档案缺的区间用 HANE 的动态档案 | 只读使用，不在本项目里改那边的数据；见下文「开播日」 |
| 已离开的旧船 | danmakus.com、LAPLACE 等弹幕存档 | 可能找回部分历史上舰记录，未验证 |

已经离开的舰长不会出现在当前名单里，所以历史上的船只能从总数曲线推算数量，无法还原是谁。

## 采集

采集程序在 `voyage/`，只用 Python 标准库。在项目根目录运行：

```powershell
uv run python -X utf8 -m voyage update   # 依次运行下面三步
uv run python -X utf8 -m voyage vtbs     # 更新 vtbs.moe 的大航海与粉丝记录
uv run python -X utf8 -m voyage guard    # 翻一遍在册名单，存一份快照
uv run python -X utf8 -m voyage build    # 不联网，只用已下载的数据合成 data/voyage.json
uv run python -X utf8 -m voyage forget <UID>   # 不联网：有人要求删掉名字时用，见下文「删除名字」
```

`build` 读取 HANE 的开播档案 `data/live_sessions.json` 和动态档案 `data/posts.json`，只读不写。HANE 的目录默认是 `../hane`，可以用 `--hane <目录>` 指定。

两次请求之间随机等 2 到 4 秒，不快于 HANE。名单每页 30 人，约 7000 人时一次要翻约 235 页、十几分钟。B 站返回风控或限流（-352、-412、-799、-509）时立即停止，不重试。

名单接口不登录也能翻完（见下面的核对）。以后如果需要登录，把 Cookie 写进项目根目录的 `config.local.toml`（已被 Git 忽略），或者设环境变量 `BILI_SESSDATA`、`BILI_BUVID3`。这个文件里有 Cookie 时，程序就带着它请求：

```toml
[bilibili]
sessdata = ""
buvid3 = ""
```

程序只把它们放进发给 B 站的请求头，不打印，也不写进任何文件。

### 存了什么

| 文件 | 内容 | 公开 |
|---|---|---|
| `data/raw/vtbs_guard.json` | vtbs.moe 的大航海人数变化，每条 `[毫秒时间, 人数]` | 否，下载缓存 |
| `data/raw/vtbs_active.json` | vtbs.moe 的粉丝数记录，每条 `[毫秒时间, 粉丝数]` | 否，下载缓存 |
| `data/guard/<北京时间>.json` | 每次翻完名单的快照：抓取时间、B 站给的总数、每人一行 `[id, 等级, 粉丝牌等级, start, 昵称]`。2026-10-22 那份没有昵称这一列 | 否，不随源码公开 |
| `data/name-removals.json` | 要求删掉名字的人：UID 的完整摘要，见下文「删除名字」 | 否，不随源码公开 |
| `data/voyage.json` | 页面用的 `VoyageData`，含昵称 | 是 |

- vtbs.moe：第一次下载全部记录。之后粉丝数只取最近 512 条，大航海人数仍取全部，因为它没有只取最近的接口。两种都只追加比已存的最后一条更晚的记录，已存的不改。最近 512 条接不上已存的记录时，自动改取全部。
- 名单：翻到最后一页，并且人数和 B 站给的总数相差不到 1%，多收、少收都算，才存快照。B 站给的总数是 0 时也不存，那更像接口出了问题。2026-10-24 以前只查少收：接口返回成功但名单是空的，也会存成快照，build 后最后一天变成 0 人、名单清空。接口不给更深的页、分页没有前进或格式变了时停止，不存快照。每页重复的前三名和翻页时重复出现的人按哈希去重。选了「神秘人」的人自己隐藏了身份，不进名单，在页面上算无名之舰。昵称取自 `uinfo.base.name`，存之前先清理：NFC 规范化；去掉控制字符、代理项、私用区和格式字符（方向控制符、零宽空格等），只留表情序列要用的连接符；换行和各种空白压成一个空格；最多 32 个码位，末尾不留半个表情序列。头像不读。快照里的 start 是快照日减陪伴天数，同一个人连续在册时它不变，所以相邻两份快照几乎相同。快照按 id 排序，不保留 B 站的排名顺序。
- 合成：日期按北京时间划分。每天取当天最后一条记录；没有记录的日子沿用前一天；第一条记录之前的日子用第一条。合成到最新一份快照为止，最后一天的总数用快照里 B 站给的数字（不少于实际取到的人数），快照之后的 vtbs.moe 记录等下一份快照再用。某天有一场直播开始，那天就算开播；直播档案缺的区间改看她的直播预告，规则见下面「开播日」。
- 有名字的船：`named` 只包含最新一份快照里的人，等级、粉丝牌等级和昵称也只用最新值；旧快照只为陪伴天数提供依据。`acc` 是 B 站的正值或下面规则回填的推定值，无依据时为 `null`。`start` 按下面三步算，不改变 `acc`，并保证任何一天有名字的船都不超过当天总数；`meta.named_by` 记下每一步各有多少人。
  1. 上舰日是快照日减 `acc` 再加 1，因为陪伴天数把上舰当天算作第 1 天。未知的人只把展示位置放在快照当天，不断言当天才上舰；查看更早日期时也显示「陪伴天数未知」。
  2. 老船优先：按上舰日从早到晚，如果从上舰日到快照日，每天的总数都多于已经确认的人数，这个人就从上舰日起一直有名字。总数掉到多少，那以前上舰的人最多就能确认多少。
  3. 确认不了的人，陪伴天数里算进了以前的任期，每段任期是整月 30 天。他的上舰日按 30 天一段往后挪，挪到第一个从那天到快照日都容得下的日子；一直挪不进去，就从快照当天起有名字。在那之前，他和已经离开的人一样，是无名之舰。
- 核实数字：`anchors` 就是下面「已核实的数字」，写在 `voyage/build.py`。合成时会打印和数据对不上的地方。

### 陪伴天数为零时

原始名单快照不修写。`build` 只对最新快照的零值寻找历史依据，最新正值保持原样，不能简单取历次最大值。回填不会增加人员、改变总人数或修改最新昵称。

1. 最多回看最近 7 个北京时间日历日。只使用原始快照里的正值，不把上次合成的推定值再次当作证据。
2. 按短哈希分组保留所有记录；这个窗口内任何一份快照出现同一哈希多人，就跳过该哈希的回填，不靠昵称、等级或排列顺序猜人。
3. 从近到远核对：双方都有非空昵称时须一致；遇到缺席就不再跨过缺席使用更早任期。若已有缺席之后的正值，可以用那一段的依据。
4. 推定天数为「历史正值 + 北京时间日期差」。多个可用正值换算后必须一致，否则保留未知。最新零值没有依据、昵称冲突或哈希有歧义时也保留未知。

`meta.accompany.backfilled` 每项记录 `{index, raw, value, from}`：最新原始名单中从 0 起的行号、原值 0、推定值和依据快照的时间。`meta.accompany.unknown` 记录 `{index, reason}`，原因是 `no_history`、`ambiguous_id`、`name_changed` 或 `conflicting_days`；`no_history` 包含超过回看范围或中间缺席。行号对应未排序的 `named`，不能用短哈希字典覆盖重复记录后再核对。命令行打印回填与未知人数。

2026-10-24 用 22 日 11:01、24 日 10:20 和 21:01 三份快照验证：最新 394 个零值中回填 393 人（364 人依据当天上午，29 人依据 22 日加 2 天），1 人没有旧记录而保留未知。满月人数由 133 恢复到 136，总人数 7190、一年以上 20 人不变，三份快照字节不变。回填后的上舰日仍经过历史总人数约束，可能同时调整其他人的历史展示位置，不能当作确切上舰记录。短哈希不重复也不能绝对证明跨快照身份一致；缺少旧昵称的匹配和跨日累加都属于推定。

同日 22:18–22:34 再次采集 240 页，取到 7190 人，新快照时间为抓取开始的 22:18:16。原始零值 316 人，回填 314 人（300 人依据 21:01，14 人依据 10:20）；1 人因短哈希重复、1 人因历史昵称不一致保留未知。与前一轮修正结果对照，两边天数都已知的 7187 人全部一致，三人的 42、43、43 天光柱仍在；总人数 7190、满月 136、一年以上 20 人不变，一年以上成员的整条记录也相同。前一轮唯一无依据的人这次取得正值 1 天。旧快照校验和及 vtbs.moe 已有记录均未改变。

### UID 的 id

`id` 是 `PBKDF2-HMAC-SHA256(UID 的十进制字符串, 盐 "hane-voyage:v1", 100000 次)` 的前 24 位，写成 6 个十六进制字符。程序读到 UID 就算出哈希，同一次抓取里用完整的哈希去重，明文 UID 不保存。完整的哈希只写进不公开的删除名单。

B 站 UID 是范围有限的整数，完整的哈希可以穷举还原。截到 24 位后只有约 1680 万个值，而旧式十位以内的 UID 有几十亿个，所以即使有人穷举全部 UID，每个 id 也对应一两百个 UID，确定不了是谁。PBKDF2 再让每次尝试变慢。代价是约 7000 人里预计有一两对 id 相同；不在名单里的人输入自己的 UID，误亮一条船的概率约万分之四。

页面的「寻舟」用浏览器自带的 WebCrypto 按同样的参数算观众输入的 UID（`src/uid.ts`），再和名单比较，UID 不离开观众的设备。`dev/test_voyage.py` 用 Node 运行这个文件，检查它和采集程序算出的 id 相同；每个 UID 约 10 毫秒。改算法时要同时改页面，并重算所有快照。

它挡不住拿一个已知的 UID 去查这个人在不在名单里，这是「输入自己的 UID 高亮」本身带来的；当前名单在 B 站直播间本来也是公开的。

### 没存什么

- 头像、明文 UID 和 B 站的排名顺序。程序只读 UID、昵称、等级、粉丝牌等级、陪伴天数五项，名单接口的原始响应不落盘。
- 分档历史：vtbs.moe 只有三档合计。快照从第一次抓取起记录分档，以后可以累积。
- 已经离开的人，原因见上文。

### 2026-10-22 的核对

先发了 9 个请求做小规模核对。B 站 7 个：1 个确认登录态有效，游客和登录各取第 1、2 页和最后一页。vtbs.moe 2 个，是第一次全量下载。之后用游客身份完整翻了一遍名单，共 237 个请求。

- 不登录也能翻到最后一页。同样的三页，游客和登录拿到的人和字段完全相同，所以采集不需要登录。
- `info.num` 是总人数（当时 7089），`info.page` 是总页数（当时 237，等于总人数除以 30 后向上取整），`info.now` 是当前页。
- 前三名（当时是 3 位总督）每一页都在 `top3` 里重复出现。`list` 每页 30 人，总人数等于 3 加上所有页的 `list`。
- 三页去重后抽到 69 人，他们的 `uinfo.medal.ruid` 都是她的 UID，所以粉丝牌等级是本直播间的。
- 陪伴天数是整数，抽到的范围是 2 到 1906 天。最后一页的人是 9 到 13 天，即 2026-10-09 到 13 日上舰，和 vtbs.moe 那几天总数的暴涨对得上。
- vtbs.moe 的记录从 2021-02-03 08:32 开始，当时大航海 0、粉丝 1683。到 2026-10-22 共有 2897 条大航海记录和 5323 条粉丝记录，没有误记成 0 的数据。大航海人数只在变化时才记一条，所以最长的空档有 26 天。
- 下面的核实数字，除了 2026-10-21 的大航海 7027，都能在 vtbs.moe 当天或前后几分钟的某条记录里找到同样的值。合成取的是每天最后一条，所以人数变化快的日子会和核实数字差一点。例如 2026-10-21 的粉丝 254840 是 vtbs.moe 在 2026-10-20 23:46 记下的值，而 21 日最后一条是 256614。

完整翻一遍名单的结果：

- 237 页约 16 分钟翻完，没有遇到风控。B 站给的总数是 7091，取到 7090 人：总督 3、提督 41、舰长 7046。少的 1 人应该是抓取期间名单前后移动造成的；没有遇到神秘人。陪伴天数 0 到 1906 天，中位数 11 天。有 3 对 id 相同，和预计的一两对相近。
- 陪伴天数把上舰当天算作第 1 天。照这个算法，10 月每天上舰的现有成员数和 vtbs.moe 当天的增量几乎一样，例如 10 月 12 日是 3607 人对 +3647。如果把上舰当天算作第 0 天，所有人就整体早了一天，所以合成时上舰日取快照日减陪伴天数再加 1。
- 离开过又回来的人，陪伴天数看来是累计的。有 134 位现有成员（舰长 131、提督 3）按陪伴天数算出的上舰日早于 2026-10-07，可 vtbs.moe 显示那几个月只有 14 到 21 人在册。这些上舰日集中在暴涨前约 30 天和 60 天，像是以前上过一两个月舰、10 月又回来的人。这一点是从数据推断的，没有 B 站的说明。
- 如果直接按陪伴天数让船入队，从 2025-07 起每天的现有成员数都会超过当天的总数，最多超出 122 人（2026-10-07）。上面「有名字的船」的三步就是为此定的。
- 第 2 步确认了 6968 人。2026 年 9 月船队只剩 14 人，所以 10 月以前上舰、一直有名字的老船正好 14 条：2021 年 8 条，2022 年 3 条，2023、2024、2026 年各 1 条。2022 年峰值那天的 1031 人里，只有这 11 条船有名字。
- 第 3 步用的 30 天有数据支持：把确认不了的 122 人按 30 天一段往后挪（先不管容不容得下），103 人正好落在 vtbs.moe 显示有人上舰、但不是已确认成员的那几天。换成 7、14、25、28、29、31、32、35、45、60 天一段都差得多，只有 30 天吻合，而大航海的一个月正好是 30 天。加上容得下的限制后，107 人挪进了 10 月，15 人从快照当天起有名字，在那之前算无名之舰。

## 开播日

篝火的亮度来自每天开没开播（页面按最近开播的频率算亮度，见上表）。直播档案缺了几段，那几段改按她在 B 站发的直播预告判定。

### 缺了哪些日子

HANE 的直播档案来自 nailv 使用的 Danmakus 公开接口，HANE 每次取回它的全部场次。缺的场次是来源本身就没有，不是采集漏掉的。HANE 在 2026-10-20 核对过：来源没有 2021 年 2 月至 9 月、2023 年 9 月至 2025 年 6 月的任何场次，2025 年 7 月只有 1 场。只看档案时，篝火在 2023-09-01 到 2025-07-26 连续 695 天不亮。可她在这段时间几乎每天发「今日も22時から配信する！！」一类的预告，所以她照常在播，只是档案没有记下来。

### 判定方法

- 档案连续 7 天以上没有场次，就算档案缺了这一段，第一场之前也算。这些区间写进 `meta.live_by_posts`，其余日子照旧只看档案。
- 在这些区间里，她发了直播预告的那天算开播。预告是 HANE 动态档案里规则标签 `tags_rule` 含「直播预告」的动态，只算她本人（UID 2094031249）发的。
- 日期按发出时间加 1 小时、再按北京时间划分。她 23 点多发「この後から配信」时，直播常在第二天零点以后才开始，档案也把这场算在第二天。

7 天这个界线来自档案里较短的空档。她真的停播的三段几乎没有预告：2021-11-07 起 6 天有 1 条，2022-10-15 起 10 天有 1 条，2026-02-20 起 14 天有 2 条。档案缺的两段每天都有预告：2025-07-28 起 7 天，2026-01-13 起 9 天。

### 准确度

2026-10-23 用档案齐全的日子核对：2021-10-02 到 2026-10-22，去掉 2023-09-01 到 2025-07-26，共 1152 天。档案有直播的 1005 天里，有 978 天发了预告。按预告算开播的 1061 天里，有 83 天档案没有直播。这 83 天有的是预告后没播，有的可能是档案缺了那一场，HANE 记有 58 场不完整的场次。

限制如下：

- 2021 年 2 月至 9 月的写法和后来不同，上面的核对覆盖不到。那时她常在直播结束后的凌晨发「谢谢来看直播，下次是某日」，这条会算到第二天，所以灯可能比实际晚一天。她在 2021-06 写过，没发预告的日子也几乎每天在播，所以这段的亮灯天数偏少。

## 名字与隐私

2026-10-24 起的规则：

- 存当前名单里非神秘人的昵称。选了神秘人的人不进名单，页面上是无名之舰。
- 陪伴一年以上的人，名字一直显示在他们船的光柱顶上，并刻在鸟居柱上。其他人的名字平时不显示，只在鼠标停在一条船上、点一条船、按名字或 UID 找船时显示。名牌上是昵称、舰长／提督／总督和那天的陪伴天数。
- 陪伴一年以上的人，每满一年，名字刻在那个月的鸟居柱上，陪伴越久，刻的门越多、字越大。离开过又回来的人，按 B 站的陪伴天数算周年，从回来那天起才刻上。
- 头像和 UID 不显示，也不保存。名单只保存 UID 的哈希（见「UID 的 id」）；观众输入的 UID 在浏览器里算哈希比对。
- 带昵称的快照和删除名单不随源码公开，公开的只有页面用的 `data/voyage.json`。
- `data/voyage.json` 里没有名字时（还没有抓到昵称），页面不显示名字，也不刻鸟居。开发服务器的地址加 `?sample-names` 会用示意名字，名牌上标「示意」；构建好的页面没有这个开关。
- B 站粉丝牌的新版配色不等于舰长／提督／总督的等级色，等级色目前是占位，待确认。

### 删除名字

有人要求删掉名字时，在项目根目录运行：

```powershell
uv run python -X utf8 -m voyage forget <UID>
uv run python -X utf8 -m voyage build
```

`forget` 可以一次给几个 UID；不给 UID 时从标准输入逐行读取。它做三件事：

1. 把这个 UID 的完整哈希加进 `data/name-removals.json`。这个文件只存哈希，不存明文 UID，不打印 UID。
2. 抹掉 `data/guard/` 已有快照里这个人的昵称。快照只有 3 字节的 id，几千人里偶尔有两人 id 相同，这时两人的名字都会抹掉。
3. 以后的抓取不再存这个人的昵称；`build` 也按 id 去掉名单里的人的昵称。

运行 `build` 并重新构建、发布页面后，这个名字才从页面上消失。限制：已经推送过的 `data/voyage.json` 留在 Git 历史里，旧版本仍能读到这个名字；要彻底删掉，需要改写仓库历史。
